## 1. 背景概述

### 1.1 项目目标

本项目面向参与者、活动组织者、检票人员和平台管理员，提供从活动创建、审核发布到报名、模拟支付、候补递补、验票签到、统计和审计的闭环。核心目标是让名额分配可追踪、角色操作有边界、异常后数据仍一致，并能用明确测试判断需求是否满足。

### 1.2 项目支持的范围

#### 项目支持对象
项目支持多个活动及可维护的活动类别。认为每个活动恰好一个场次、一个票种，每名参与者每次只为本人购买一张票；不同活动可以有不同时间、价格和容量。
#### 项目实现的功能
实现账号与角色权限、活动审核、单场次单票种配置、多条件查询、待支付名额占用、模拟支付与退款、自动候补、电子票、检票人员验票、举报处理、名单导出、容量统计和操作记录。报名、支付、退款、递补和签到的关联状态保持一致。
#### 项目不支持的内容
1. 不接入真实支付或银行服务，点击“确认支付”或“退票并确认退款”只改变系统中的订单、报名、票和库存状态。活动取消时系统自动执行相同的模拟退款。
2. 不接入真实短信、微信或邮件，通知以站内消息或页面提示完成；
3. 不实现实名认证、选座和外部地图、营销服务。
4. 已发布活动不能通过下架、改价、重新审核来沿用原票，关键信息有误时须在活动开始前取消并另建活动。

### 1.3 各角色及权限

| 角色 | 可以干 | 不可以干 |
| --- | --- | --- |
| 参与者 | 查询活动，报名、模拟支付、退票、候补，查看本人记录与票，举报活动 | 发布、审核、验票、下架活动；查看他人名单 |
| 活动组织者 | 创建草稿、提交或撤回审核、修改允许的字段、取消本人活动、查看本活动名单和统计 | 审核、验票、购买本人活动的票、举报；发布后直接修改价格、容量、地点和时间 |
| 检票人员 | 使用管理员创建并线下交付的账号，选择活动后核验该活动电子票、签到、查看和导出名单；系统不管理逐活动授权 | 购票、修改或发布活动、下架活动、举报；对所选活动使用其他活动的票验票 |
| 平台管理员 | 维护类别和工作人员账号，审核活动、核查举报、依据举报下架、处理权限限制、查询审计记录 | 代组织者创建活动、代参与者报名、直接取消用户订单、无举报依据下架活动 |
| 未登录者 | 注册、登录和查询公开活动 | 其他啥都不能干 |

## 2. 需求分析

### 2.1 主流程与分支

| 阶段 | 正常流程 | 关键分支或失败处理 |
| --- | --- | --- |
| 活动筹备 | 组织者保存草稿 → 提交审核 → 管理员通过并发布 | 组织者可撤回审核；管理员驳回须说明原因；放票结束后不能审核通过 |
| 报名与付款 | 放票期有名额时生成待支付订单并占位 → 15 分钟内点击确认支付 → 生成唯一电子票 | 售罄可候补；重复报名返回原记录；超时、取消或故障只释放一次名额 |
| 候补递补 | 退票或超时释放名额 → 在规定时间内按服务端入队顺序递补 → 新订单有 15 分钟支付期 | 不允许新报名者越过可递补队列；距开始不足 12 小时不再递补 |
| 到场与结束 | 检票员在活动进行中选择活动并核对有效票 → 签到 → 活动结束标记未到者缺席 | 错活动票、无效票、重复扫码、活动结束后签到均拒绝 |
| 举报与取消 | 参与者举报 → 管理员核查；组织者可在活动开始前取消 | 举报属实且未开始可下架并模拟退款；开始后只能记处理结论和违规，不改变已签到结果 |

### 2.2 核心数据和约束

一个组织者可以创建多个活动，一个活动归属一个组织者；活动在第一版固定关联一个场次和一个票种，票种价格、容量及放票时间属于该活动的配置。参与者可对不同活动分别报名，但同一活动同时只能有一条未结束的报名记录。报名记录关联参与者、活动和订单；订单支付成功后生成一张电子票。票码全局唯一，票保留与持票人、活动和订单的映射，不能转让或换人。

候补记录按服务端写入的递增编号排序，不占库存。当前占用名额数等于有效待支付订单数加已支付且未退款订单数；剩余名额等于活动总容量减去占用名额数，必须始终不小于零。支付、退款、递补和签到在更新相关记录时整体成功或整体失败，同一请求重试只生效一次。20 人并发抢最后一个名额时仅一人取得待支付订单。

举报关联举报人和活动，同一参与者对同一活动只可举报一次。关键操作日志关联操作人、业务对象、操作前后状态、时间、结果和请求标识；普通业务数据在活动结束后 180 天内可按权限查看，期满后不供普通页面和导出接口访问，底层数据与审计日志归档留存。

### 2.3 业务状态与转换

| 对象 | 主要状态及允许转换 | 禁止或受限的转换 |
| --- | --- | --- |
| 活动 | 草稿 → 审核中 → 已发布；审核中经撤回或驳回回到草稿；已发布在开始前可变为已取消，举报属实且开始前可变为已下架 | 审核中不能直接修改；已发布不能直接改时间、地点、票价或容量；开始后不能取消或下架 |
| 订单 | 待支付 → 已支付／已取消／已超时；已支付 → 已退款 | 已支付不能回到待支付；已退款、已取消和已超时不能恢复为有效订单（REQ-031） |
| 报名记录 | 候补中 → 待支付 → 购票成功 → 已签到，或在活动结束后转缺席；取消、退款和活动终止走相应终态 | 终态不能逆转；重新报名须生成新记录并重新排队 |
| 电子票 | 支付后生成有效票；有效 → 已验票，或因退款、取消、下架变为已失效 | 已验票、已失效不能重新变为有效；重复验票不新增签到 |

验票时间按服务器北京时间判断，活动开始时刻可验票，结束时刻及之后不可验票。报名截止后的旧页面请求由服务端重新检查状态并拒绝；支付超时和缺席标记由定时任务及相关请求时的到期检查共同处理，程序重启后也须补处理。

## 3. 非功能性需求

- **权限与安全（REQ-027）**：以未登录者及四类角色直接调用受限接口，未授权操作成功次数为零；密码不得明文展示或存储。
- **并发与可靠性（REQ-028～REQ-029）**：执行 20 抢 1、10 抢 5，以及重复支付、退款、签到和故障注入；核对成功人数、库存、票映射与日志，不能超卖或部分更新。
- **查询性能（REQ-030）**：在事先约定并记录的测试机器上预置 1000 个活动、20 个并发查询用户，连续 100 次查询至少 95 次在 2 秒内成功返回，失败和超时计入未达标。
- **可恢复操作（REQ-034）**：断网或页面加载失败时给出失败提示和重新加载入口；恢复后用户可查看本人订单或票的最终状态，重复请求不会再次生效。
- **名单与统计（REQ-022～REQ-024）**：按角色限定名单可见范围和 CSV 导出字段；展示人数、容量及比率，并对退票与零分母场景进行验算。公式和分母已明确，待补甲方访谈确认其来源。

## 4. 实验总结

### 4.1 访谈和整理中的困难
主要苦难是前几轮访谈覆盖范围较大，几乎是想当什么问什么，想到什么补充什么，而且前后我们两个人的想法可能发生了改变，同一对象的状态曾混用。例如最初把“未支付、已支付、已报名”写在报名状态中，随后将订单、报名和票分别建模（INT-01-L030、INT-02-L018）。后续沟通又将多场次多票种收敛为单场次单票种，将候补的“24 小时确认资格＋付款”改为直接递补后的 15 分钟付款，并把真实支付排除在范围外（INT-04-L002、L008、L010）。整理时保留了原访谈记录，在最终需求中才采用后续明确确认的方式。
### 4.2 AI 使用

使用 Codex 桌面应用的 GPT-6，以访谈材料及课程字段要求生成结构化初稿，再逐条核对来源、角色边界、状态、异常和验收方法。AI 帮助我们快速组织和调整了需求编号与字段，但是使用的时候需要强调和检查，不能让AI替甲方决定遗漏的业务口径，也可能把不同对象状态混写，需要明确告诉它问题在哪，出现问题标注而不是自己填写。

本次人工审查保留了初稿中有依据的流程，并在 `chat.txt` 的 REV-001～REV-006 记录代表性修改：补充登录后主动改密（REQ-033）、支付成功与活动取消提示（REQ-008、REQ-011）、签到率等统计（REQ-023）、明确四角色禁止操作（REQ-027）、网络故障提示与结果查验（REQ-034），以及简化检票员权限范围（REQ-017、REQ-022、REQ-024）。
